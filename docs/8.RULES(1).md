# Dearr --- Project AI Rules

> **V1 infrastructure:** Hostinger (Node.js hosting + MySQL + file
> storage) with Dearr application authentication.

**Version:** V1\
**Project:** Dearr E-commerce Website\
**Development Environment:** Antigravity IDE\
**Developer:** Beginner / Solo

## 1. Project Context

Dearr is a V1 e-commerce website with: - Customer storefront -
Founder/Admin dashboard - Product management - Categories - Discounts -
Wishlist - Cart - Checkout - Orders - Payments

**Stack:** Next.js + TypeScript, Tailwind CSS, Next.js Route Handlers,
Hostinger MySQL, Dearr Application Auth, Hostinger File Storage,
Razorpay, Hostinger Node.js hosting, Git/GitHub.

Source-of-truth documents live in `/docs`: - `PRD.md` - `TRD.md` -
`SCHEMA.md` - `APPFLOW.md` - `DESIGN.md` - `IMPLEMENTATION.md` -
`TRACKER.md` - `RULES.md`

## 2. Golden Rules

1.  Follow PRD, TRD, and SCHEMA exactly.
2.  Work in small, reviewable steps.
3.  Do one logical task at a time.
4.  Do not touch unrelated code.
5.  Never rewrite large sections without asking first.
6.  If a requirement is unclear, ask before assuming.
7.  Prefer simple, readable solutions over clever solutions.
8.  Respect the Dearr V1 scope.
9.  Do not add V2/V3 features without approval.
10. Reuse existing components, helpers, and patterns.
11. Keep customer and admin functionality clearly separated.
12. Never silently change architecture, database structure, or business
    rules.

## 3. Code Style

-   Match existing code patterns.
-   Keep functions small and single-purpose.
-   Keep components focused.
-   Separate UI, validation, business logic, and data access where
    practical.
-   Add comments only for non-obvious logic.
-   No dead code.
-   No commented-out code blocks left behind.
-   No unused imports or variables.
-   Use the project's formatter and linter.

## 4. Naming

-   Variables/functions: `camelCase`
-   Components/classes: `PascalCase`
-   Files: follow project convention; prefer `kebab-case` where no
    convention exists.
-   Database tables/columns: `snake_case`
-   API paths: follow `TRD.md`
-   Use descriptive names.

Avoid names such as `x`, `tmp`, `data2`, `thing`, `stuff`.

## 5. Architecture & Files

-   Respect the folder structure defined in the docs.
-   Keep UI, server logic, validation, and data access separated.
-   Do not create new top-level folders without asking.
-   Do not create a separate backend service for V1.
-   Do not introduce microservices, Redis, Elasticsearch, or similar
    infrastructure unless explicitly approved.
-   Keep server-only code server-side.
-   Never expose server secrets to browser code.

## 6. Database Rules

`SCHEMA.md` is the database source of truth.

-   Never invent tables or columns.
-   Never silently rename database fields.
-   Avoid duplicate business data.
-   Historical order snapshots are intentional and must be preserved.
-   Never reconstruct old order totals from current product prices.
-   Store money as numeric values, not formatted strings such as
    `"₹499"`.

If a feature needs a schema change: 1. Stop. 2. Explain why the current
schema is insufficient. 3. Propose the exact change. 4. Get approval. 5.
Update `SCHEMA.md`. 6. Update the migration and affected code.

## 6.5 Hostinger Infrastructure Rules

-   Hostinger is the V1 deployment target.
-   Use Hostinger MySQL for structured application data.
-   Use the Hostinger application's persistent upload directory for
    product images.
-   Keep database credentials and session secrets in Hostinger
    environment variables.
-   Do not assume the 50 GB disk limit is the same as the MySQL database
    limit; verify database limits in hPanel.
-   Do not store image binaries inside MySQL; store file paths/URLs in
    `product_images`.
-   Use Hostinger's backup/restore facilities and verify a restore
    before production launch.

## 7. Authentication & Authorization

Use **Dearr Application Auth**: - MySQL `profiles` table stores the
account email, bcrypt password hash, and role. - `bcryptjs` handles
password hashing/verification. - `jose` signs the session payload. -
Sessions are stored in secure HTTP-only cookies.

-   Authentication = who the user is.
-   Authorization = what the user can do.
-   Check admin authorization on the server.
-   Never trust a role value from the browser.
-   Customers can access only their own orders, carts, wishlists, and
    addresses.
-   Protect `/admin` and admin APIs.
-   Handle expired sessions safely.
-   Never store plaintext passwords; store only bcrypt hashes generated
    on the server.

## 8. Security --- Non-Negotiable

-   Never hardcode secrets, passwords, API keys, or payment secrets.
-   Use environment variables.
-   Never expose `DB_PASSWORD`, `SESSION_SECRET`, or
    `RAZORPAY_KEY_SECRET` to client code.
-   Use HTTPS in production.
-   Do not store raw card data or card security codes.
-   Never log passwords, access tokens, payment secrets, or sensitive
    credentials.
-   Validate all user input on the server.
-   Safely render untrusted content.
-   Protect against SQL injection, cross-site scripting (XSS),
    unauthorized admin access, forged payment results, insecure uploads,
    and accidental data exposure.
-   Never trust client-supplied price, discount, stock, payment status,
    or admin role.
-   Recalculate or verify critical values server-side.
-   Verify payment on the server before marking an order paid.

## 9. Design & UX

`DESIGN.md` is the visual source of truth.

Dearr V1 design values:

``` text
Primary       #A2CB8B
Secondary     #FFCB56
Success       #2A7C13
Warning/Error #C00707
Display Font  Telma
UI Font       Inter
Spacing       8px base grid
```

Rules: - Design mobile-first. - Do not introduce random colors or
fonts. - Reuse shared components. - Important screens should handle
loading, empty, error, and success states. - Avoid dead-end screens. -
Keep one clear primary action on important screens.

## 10. App Flow

`APPFLOW.md` is the navigation/behavior source of truth.

-   Follow documented customer and admin flows.
-   Check affected flows before changing routes or behavior.
-   Do not silently remove a route.
-   Every error state needs a recovery path.
-   New screens require explanation and documentation updates before
    implementation.

## 11. API & Business Logic

-   Follow API patterns in `TRD.md`.
-   Validate requests before database writes.
-   Return safe errors.
-   Do not expose stack traces or internal database details.
-   Keep money, permissions, stock, order state, and payment rules on
    the server.

The server is the source of truth for:

``` text
Final Price
Discount
Stock
Order Total
Payment Status
Admin Authorization
```

## 12. Product & Inventory

-   Only active products should normally appear on the storefront.
-   Inactive products must not be purchasable.
-   Check stock before checkout.
-   Never create negative stock.
-   Prefer deactivation instead of hard deletion when historical orders
    depend on a product.
-   Follow `SCHEMA.md` for variants.

## 13. Discount Rules

-   Follow the discount model in `SCHEMA.md`.
-   Validate percentage values and date ranges.
-   Check active status and valid dates.
-   Do not invent discount-stacking behavior.
-   If overlapping discounts are possible and no priority rule exists,
    stop and ask.
-   Never trust browser-provided discount values.

## 14. Payment Rules

Use Razorpay according to `TRD.md`.

-   Use test mode first.
-   Create payments from trusted server-side order data.
-   Verify payments on the server.
-   Never mark an order paid only because the browser says payment
    succeeded.
-   Handle success, failure, cancellation, and delayed/unknown states.
-   Keep payment secrets server-side.

## 15. Testing & Quality

After implementing a task: 1. Explain briefly how to test it. 2. Test
the happy path. 3. Test at least one relevant edge/error case. 4. Check
affected flows for regressions. 5. Confirm there are no relevant errors.
6. Do not mark work complete until it works.

For UI: - Test mobile. - Test loading/empty/error states. - Test main
interactions. - Check browser console.

For APIs: - Test valid and invalid input. - Test
authentication/authorization. - Test database behavior.

For database: - Test constraints, foreign keys, ownership/security, and
representative reads/writes.

For payments: - Test success, failure/cancellation, and server-side
verification.

## 16. Git / Commits

Use Conventional Commits:

``` text
feat:
fix:
docs:
refactor:
chore:
test:
```

Rules: - One logical change per commit. - Keep commits small. - Do not
mix unrelated refactors with feature work. - Suggest a commit message
after completing a task.

## 17. Tracker Discipline

`TRACKER.md` is the progress source of truth.

Before starting:

``` text
To Do → In Progress
```

After finishing:

``` text
In Progress → Done
```

Only mark Done when the task is implemented, tested, working, and
committed.

When blocked:

``` text
In Progress → Blocked
```

Write the exact blocker in `Notes/Blockers`.

If a new task or bug is discovered: - Add it to `TRACKER.md`. - Give it
a clear title. - Assign a priority. - Add a short note.

## 18. Documentation Discipline

Keep documentation synchronized with implementation:

``` text
Product behavior       → PRD / APPFLOW
Technical architecture → TRD
Database structure     → SCHEMA
Visual/UI              → DESIGN
Build sequence         → IMPLEMENTATION
Progress               → TRACKER
AI rules               → RULES
```

## 19. How to Respond to Henry

-   Be concise.
-   Before large changes, show a short plan.
-   State important assumptions at the top.
-   Explain non-obvious decisions in plain language.
-   Mention dependencies before dependent tasks.
-   Flag anything risky, irreversible, security-sensitive,
    payment-related, database-changing, or outside V1 scope.
-   Do not overwhelm with unnecessary jargon.
-   After a task is complete, summarize:
    1.  What changed.
    2.  How to test it.
    3.  Suggested commit message.
    4.  Tracker status.

## 20. Do Not

-   Do not add dependencies without explaining why.
-   Do not add V2/V3 features without approval.
-   Do not change the schema silently.
-   Do not change config/build/deployment files without explaining the
    impact.
-   Do not perform huge multi-file rewrites in one step.
-   Do not rewrite unrelated code.
-   Do not hardcode secrets.
-   Do not expose server-only environment variables.
-   Do not bypass authentication/authorization.
-   Do not trust client-side price or payment values.
-   Do not invent undocumented business rules.
-   Do not create duplicate components when reusable ones already exist.
-   Do not delete working code merely to use a different style.
-   Do not mark a task Done if it has not been tested.

## 21. V1 Scope Guard

Before adding a feature:

``` text
Is it in Dearr V1?
       │
   ┌───┴───┐
  YES     NO
   │        │
 Build    Ask first
```

When uncertain, ask instead of guessing.

## 22. Final Rule

**Build the smallest correct Dearr V1, one task at a time, while keeping
code, database, documentation, and tracker in sync.**
