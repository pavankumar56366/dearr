# Dearr --- Database Schema

> **V1 infrastructure:** Hostinger (Node.js hosting + MySQL + file
> storage) with Dearr application authentication.

**Version:** V1\
**Database:** MySQL 8.x (Hostinger)\
**Provider:** Hostinger MySQL\
**Naming convention:** `snake_case`\
**Related Documents:** `Dearr_PRD.md`, `Dearr_TRD.md`,
`Dearr_APPFLOW.md`, `Dearr_DESIGN.md`

------------------------------------------------------------------------

## 1. Overview

Dearr V1 uses a relational MySQL database on Hostinger to store customer
accounts/profiles, products, categories, product image paths, optional
variants, wishlists, carts, discounts, orders, delivery addresses, and
payment records. The schema is normalized so the same information is not
repeatedly stored in unrelated tables. Because Dearr no longer uses an
external authentication provider, the `profiles` table also stores the
login email, bcrypt password hash, role, and password-reset metadata
needed by the application. Historical order data preserves the price and
product name used when the order was placed, so future product changes
do not rewrite old orders.

### Tables

  -----------------------------------------------------------------------
  Table                               Purpose
  ----------------------------------- -----------------------------------
  `profiles`                          Application-level customer/admin
                                      profile linked to the
                                      authentication user.

  `categories`                        Stores product categories.

  `products`                          Stores the main product catalog and
                                      current pricing/stock.

  `product_images`                    Stores product image metadata and
                                      display order.

  `product_variants`                  Stores optional choices such as
                                      color or size for products that
                                      need them.

  `wishlists`                         Stores one wishlist for a customer.

  `wishlist_items`                    Join table connecting wishlists to
                                      products.

  `carts`                             Stores a customer's active shopping
                                      cart.

  `cart_items`                        Join table connecting carts to
                                      products/variants and quantities.

  `discounts`                         Stores discount rules, dates,
                                      status, and scope.

  `discount_products`                 Join table for discounts that apply
                                      to specific products.

  `discount_categories`               Join table for discounts that apply
                                      to categories.

  `addresses`                         Stores reusable customer delivery
                                      addresses.

  `orders`                            Stores a purchase snapshot and
                                      order-level information.

  `order_items`                       Stores the products, quantities,
                                      and prices captured in each order.

  `payments`                          Stores payment-provider references
                                      and payment status.

  `reviews`                           Customer product reviews, ratings,
                                      and moderation status.

  `store_settings`                    Global store settings, checkout limits,
                                      shipping fees, and configuration.
  -----------------------------------------------------------------------

### Rules

-   `id` is generated by the application as a UUID string.
-   `email` must be unique.
-   `password_hash` must contain only a bcrypt hash, never a plaintext

-   `role` must be restricted to approved values.
-   Admin access must be checked server-side; changing browser data must
    never grant admin access.

## 2.10 `discounts`

Discount definitions live in one place. Product/category assignment is
handled by join tables.

  ------------------------------------------------------------------------------------
  Column            Data Type         Constraints           Description
  ----------------- ----------------- --------------------- --------------------------
  `id`              `char(36)`        **PK**, not null,     Unique discount ID.
                                      default generated     

  `name`            `text`            not null              Internal/customer-facing
                                                            discount name.

  `code`            `text`            nullable, **unique    Optional coupon/code.
                                      when present**        

  `discount_type`   `text`            not null              `percentage` or
                                                            `fixed_amount`.

  `value`           `decimal(10,2)`   not null, check `> 0` Discount amount or
                                                            percentage value.

  `scope`           `text`            not null              `store`, `category`, or
                                                            `product`.

  `start_at`        `datetime`        not null              Discount start time.

  `end_at`          `datetime`        nullable              Discount end time; null
                                                            means no fixed end.

  `is_active`       `tinyint(1)`      not null, default     Manual enable/disable
                                      `true`                switch.

  `created_at`      `datetime`        not null, default     Creation time.
                                      `CURRENT_TIMESTAMP`   

  `updated_at`      `datetime`        not null, default     Last update time.
                                      `CURRENT_TIMESTAMP`   
  ------------------------------------------------------------------------------------

### Discount validation rules

-   Supported scopes (3 scopes): `store`, `category`, and `product`.
-   Percentage discounts must be between `0 < value <= 100`.
-   Fixed amount discounts must be positive (`value > 0`).
-   `end_at`, when present, must be strictly later than `start_at`.
-   The application must determine whether an offer is currently valid
    using `is_active = 1`, `start_at <= NOW()`, and `(end_at IS NULL OR NOW() < end_at)`.
-   **Precedence rule:** `product` > `category` > `store`.
-   **Strictly NO stacking:** Discounts are never combined or stacked.
-   **Overlap conflict prevention:** Conflicting discounts of the same applicable scope and target in overlapping date ranges are rejected with `409 Conflict`.

### Why does the order contain shipping fields if `addresses` exists?

Because historical orders must not change when a customer edits or
deletes their saved address later. The `addresses` table is reusable
customer data; the order stores a purchase-time snapshot.

The `store_settings` table stores global application configuration (contact information, order thresholds, free shipping threshold, COD toggles, cancellation window, and notification settings) for the store. A single row (`id = 1`) contains the JSON configuration document.

  ---------------------------------------------------------------------------------
  Column                  Data Type         Constraints           Description
  ----------------------- ----------------- --------------------- -----------------
  `id`                    `int`             **PK**, default `1`   Single record identifier.

  `settings_json`         `json`            not null              Serialized store
                                                                  configuration payload.

  `created_at`            `datetime`        not null, default     Settings creation
                                            `CURRENT_TIMESTAMP`   timestamp.

  `updated_at`            `datetime`        not null, default     Last update timestamp
                                            `CURRENT_TIMESTAMP`   (auto-updated on change).
  ---------------------------------------------------------------------------------

### Rules

- Only authenticated administrators (`requireAdmin()`) can update `store_settings`.
- If the record does not exist, the server falls back to safe `DEFAULT_ADMIN_SETTINGS`.
- When an administrator modifies settings via `/api/admin/settings`, the JSON document is updated in Hostinger MySQL and immediately consumed by checkout/order operations.

# 3. Relationships

## 3.1 Users / Profiles

**One-to-one**

``` text
profiles.id  ─────  application session user id
```

One Dearr account has one `profiles` record and can have one active
application session at a time per browser.

------------------------------------------------------------------------

## 3.2 Categories → Products

**One-to-many**

``` text
categories.id  ─────<  products.category_id
```

One category can contain many products. A product belongs to at most one
category in V1.

------------------------------------------------------------------------

## 3.3 Products → Images

**One-to-many**

``` text
products.id  ─────<  product_images.product_id
```

One product can have multiple images.

------------------------------------------------------------------------

## 3.4 Products → Variants

**One-to-many**

``` text
products.id  ─────<  product_variants.product_id
```

One product can have zero or many variants.

------------------------------------------------------------------------

## 3.5 Profiles → Wishlist

**One-to-one**

``` text
profiles.id  ─────  wishlists.user_id
```

One customer has one wishlist in V1.

------------------------------------------------------------------------

## 3.6 Wishlist ↔ Products

**Many-to-many**

``` text
wishlists.id  ─────<  wishlist_items  >─────  products.id
```

A wishlist can contain many products, and a product can appear in many
customers' wishlists.

------------------------------------------------------------------------

## 3.7 Profiles → Carts

**One-to-many historically, one active cart operationally**

``` text
profiles.id  ─────<  carts.user_id
```

A customer may have multiple historical carts, but application logic
should normally allow only one active cart per customer.

------------------------------------------------------------------------

## 3.8 Carts ↔ Products

**Many-to-many through `cart_items`**

``` text
carts.id  ─────<  cart_items  >─────  products.id
```

A cart contains many products and a product can appear in many carts.

`cart_items.variant_id` optionally points to the selected product
variant.

------------------------------------------------------------------------

## 3.9 Discounts ↔ Products

**Many-to-many through `discount_products`**

``` text
discounts.id  ─────<  discount_products  >─────  products.id
```

One discount can apply to many specific products, and one product can
have multiple discount definitions over time.

------------------------------------------------------------------------

## 3.10 Discounts ↔ Categories

**Many-to-many through `discount_categories`**

``` text
discounts.id  ─────<  discount_categories  >─────  categories.id
```

One discount can apply to many categories, and a category can
participate in many discounts over time.

------------------------------------------------------------------------

## 3.11 Profiles → Addresses

**One-to-many**

``` text
profiles.id  ─────<  addresses.user_id
```

One customer can save multiple addresses.

------------------------------------------------------------------------

## 3.12 Profiles → Orders

**One-to-many**

``` text
profiles.id  ─────<  orders.user_id
```

One customer can have many orders.

The foreign key can be nullable if guest checkout is enabled.

------------------------------------------------------------------------

## 3.13 Orders → Order Items

**One-to-many**

``` text
orders.id  ─────<  order_items.order_id
```

One order contains one or more purchased items.

------------------------------------------------------------------------

## 3.14 Products → Order Items

**One-to-many historically**

``` text
products.id  ─────<  order_items.product_id
```

A product can appear in many orders.

The reference is nullable because historical orders must remain readable
even if a product is later removed.

------------------------------------------------------------------------

## 3.15 Orders → Payments

**One-to-many**

``` text
orders.id  ─────<  payments.order_id
```

An order can have more than one payment record, for example when a
failed payment is followed by a successful retry.

------------------------------------------------------------------------

# 7. Notes

## 7.1 Normalization

Normalization means storing each kind of information in the table where
it belongs instead of repeating the same data in many places.

Examples:

-   Category name lives in `categories`, not repeated in every product
    as text.
-   Product images live in `product_images`, not as multiple image
    columns on `products`.
-   Wishlist membership lives in `wishlist_items`, not as a list inside
    `profiles`.
-   Product-specific discount assignments live in `discount_products`.
-   Category-specific discount assignments live in
    `discount_categories`.

This keeps updates consistent and reduces duplicate data.

------------------------------------------------------------------------

## 7.2 Why Historical Order Data Is Different

Normally we avoid duplicate data. Orders are the important exception.

For example, a product is currently:

``` text
Love Mug
Price = ₹499
```

A customer buys it. Later the founder changes the product price to:

``` text
Love Mug
Price = ₹599
```

The old order must still show the original purchase information.
Therefore `order_items` intentionally stores:

-   `product_name`
-   `variant_name`
-   `unit_price`
-   `quantity`
-   `discount_amount`
-   `line_total`

This is a historical snapshot, not accidental duplication.

------------------------------------------------------------------------

## 7.3 Product Deactivation vs Deletion

Do not hard-delete normal products that may already be connected to
order history.

Preferred flow:

``` text
Active Product
     ↓
Deactivate
     ↓
is_active = false
     ↓
Hidden from storefront
     ↓
Historical orders remain intact
```

------------------------------------------------------------------------

## 7.4 Discount Conflicts

V1 should define one clear rule when multiple discounts could apply.

A simple V1 rule is:

``` text
Store-wide discount
OR
Category discount
OR
Product discount
```

Choose one applicable discount according to a documented priority rule,
rather than silently stacking discounts.

The exact priority should be finalized before implementation.

------------------------------------------------------------------------

## 7.5 Money

Use `decimal(10,2)` rather than floating-point numbers for monetary
values.

Store:

``` text
499.00
```

Not:

``` text
"₹499"
```

The UI can format the numeric value as Indian Rupees (`₹`) when
displaying it.

------------------------------------------------------------------------

## 7.6 Timestamps

Use `datetime` for timestamps so dates remain unambiguous across
environments and deployment locations.

------------------------------------------------------------------------

## 7.7 IDs

Use UUID (Universally Unique Identifier) values for primary keys in
application tables. This avoids exposing predictable sequential IDs and
works well for application-level identifiers and does not expose
sequential IDs.

Customer-facing order numbers can still be shorter and human-friendly,
such as:

``` text
DEAR-10001
```

------------------------------------------------------------------------

## 7.8 Foreign Key Delete Behavior

Recommended defaults:

-   Product → images: deleting/deactivating a product should not
    silently remove historical order information.
-   Wishlist → wishlist items: deleting a wishlist can cascade-delete
    its items.
-   Cart → cart items: deleting a cart can cascade-delete its items.
-   Order → order items: if an order is ever deleted in an internal
    cleanup process, related items can cascade only when business/legal
    requirements allow it.
-   Category → products: do not automatically delete products when a
    category is removed. Prefer deactivation or reassignment.
-   Product → order items: use a nullable foreign key so historical
    orders remain readable.

------------------------------------------------------------------------

## 7.9 Admin Roles

For V1, `profiles.role` can remain simple:

``` text
customer
admin
```

Do not build complex permissions until multiple staff roles are actually
needed.

------------------------------------------------------------------------

## 7.10 MySQL Application-Level Authorization

Hostinger MySQL does not provide the previous external provider's
row-level authorization layer. Dearr therefore enforces authorization in
the Next.js server/API layer.

Recommended V1 rules:

-   Customers can read active storefront products.
-   Customers can manage only their own wishlist.
-   Customers can manage only their own cart.
-   Customers can read only their own orders.
-   Customers can manage only their own saved addresses.
-   Admin operations require a valid server-side session whose role is
    `admin`.
-   Never trust a role value sent by the browser.
-   Every customer-owned query must include the authenticated user's ID.
-   Every admin mutation must perform a server-side role check.

------------------------------------------------------------------------

## 7.11 Data That Should NOT Be Stored

Do not store:

-   Raw passwords. Only bcrypt password hashes may be stored in
    `profiles`.
-   Full card numbers.
-   Card CVV/security codes.
-   Payment-provider secret keys.
-   Unnecessary personal information.
-   Formatted price strings in database fields.

------------------------------------------------------------------------

## 7.12 V1 Simplification

This schema supports future growth, but V1 does not need every optional
table to be heavily used on day one.

For example:

``` text
No variants required?
→ products.stock_quantity is enough.

No guest checkout?
→ carts.session_token and nullable orders.user_id can remain unused.

No coupon codes?
→ discounts.code can remain NULL.

No category-specific discount?
→ discount_categories stays empty.
```

The schema should support the product direction without forcing unused
complexity into the UI.

------------------------------------------------------------------------

# 8. Suggested V1 Validation Rules

Before a record is saved, enforce at least these rules:

### Products

-   Name is not empty.
-   Description is not empty.
-   Price is `>= 0`.
-   Stock is `>= 0`.
-   Slug is unique.

### Categories

-   Name is not empty.
-   Slug is unique.

### Discounts

-   Value is greater than zero.
-   Percentage is not greater than 100.
-   End date, when present, is after start date.
-   Scope matches the relevant assignment table.

### Cart

-   Quantity is greater than zero.
-   Product must be active.
-   Product/variant must have sufficient stock before checkout.

### Orders

-   Order totals must be calculated server-side.
-   Order item price must come from trusted product/variant/discount
    data.
-   Payment status must not be marked `paid` from browser input alone.

# 10. V1 Schema Principle

**Keep current catalog data normalized, but deliberately snapshot the
information required to preserve historical orders.**

The database should be simple enough for a beginner to understand,
strict enough to prevent inconsistent data, and flexible enough to
support Dearr's later V2 features without replacing the core structure.

# 11. Category Browsing Metrics (Migration 004 — Local Unapplied)

### `category_views` Table

Stores discrete customer category navigation and browse events for genuine category popularity rankings.
Designed with session-window rate and duplication limiting to prevent inflating metrics on rapid re-renders or bot requests.

| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `id` | VARCHAR(36) | PRIMARY KEY | Unique UUID identifier for the browse event |
| `category_id` | VARCHAR(36) | NOT NULL, FK -> `categories(id)` ON DELETE CASCADE | Category that was viewed |
| `viewed_at` | DATETIME | NOT NULL DEFAULT CURRENT_TIMESTAMP | Timestamp of view |
| `session_hash` | VARCHAR(64) | NULL | SHA-256 hash / session identifier for 30-minute deduplication window |

**Indexes:**
- `PRIMARY KEY (id)`
- `KEY idx_cat_views_category_time (category_id, viewed_at)`
- `KEY idx_cat_views_session_window (category_id, session_hash, viewed_at)`

**Status:** Local unapplied migration. (Not executed against Hostinger production).
