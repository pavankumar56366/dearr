# Dearr --- Technical Requirements Document (TRD)

> **V1 infrastructure:** Hostinger (Node.js hosting + MySQL + file
> storage) with Dearr application authentication.

**Version:** V1\
**Product:** Dearr E-commerce Website\
**Audience:** Beginner developers building with Antigravity\
**Related Document:** `Dearr_PRD.md`

------------------------------------------------------------------------

## 1. Overview

Dearr V1 will be a single web application containing two connected
experiences: a customer-facing e-commerce storefront and a protected
founder/admin dashboard. The application will support product browsing,
search, categories, product details, wishlist, cart, checkout, customer
accounts, order creation, and basic order management. The admin side
will let the founder add and edit products, manage categories and
discounts, and view/update orders. To keep V1 beginner-friendly and
avoid unnecessary complexity, the application should use one main web
codebase, Hostinger MySQL for application data, application-managed
authentication, Hostinger file storage for product images, and a hosted
payment provider instead of a separate backend server or microservices.

### Architecture Explanation

There is one main Dearr web application.

- **Customer pages** handle browsing and shopping.
- **Admin pages** handle store management.
- **Next.js Route Handlers** perform sensitive operations on the server.
- **Hostinger** provides the Node.js runtime, MySQL database, and persistent file storage; Dearr implements authentication and authorization in the application.
- **Razorpay** handles payment processing.
- The frontend should never receive secret credentials such as a database service key or payment secret.


### Important rule

The browser must not be trusted to decide the final price, discount,
stock quantity, or payment status. The server must recalculate or verify
these values using trusted database/payment-provider information.

### V1 Discount Rules & Precedence

1. **Supported Scopes (3 scopes):**
   - `Store-wide` (`store`): Applies to all eligible products in the store.
   - `Category-wise` (`category`): Applies to all products belonging to the selected category.
   - `Specific Product` (`product`): Applies exclusively to the targeted product.

2. **Precedence Hierarchy:**
   When a product matches multiple active discounts, Dearr V1 applies strict priority:
   `Specific Product` > `Category-wise` > `Store-wide`

3. **No Discount Stacking:**
   Discounts are strictly never stacked or summed together. Exactly one applicable discount is resolved per product context.

4. **Same-Priority Conflict Prevention:**
   Creating or updating active/scheduled discounts that target the same scope/entity across an overlapping time period is prohibited and rejected with `409 Conflict`.

### V1 Wishlist Rules & Ownership Architecture

1. **One Customer = One Wishlist:**
   - Enforced by database `UNIQUE (user_id)` constraint on `wishlists`.
   - Server helper `getOrCreateWishlistForUser(userId)` transparently initializes a customer wishlist on demand while preventing duplicate rows.

2. **Server-Derived Authenticated Ownership:**
   - Identity is derived strictly from the verified session cookie via `requireUser()`.
   - Never trusts client-supplied `userId` or `wishlistId` (prevents IDOR vulnerabilities).
   - All read/write queries join `wishlists` and filter by `wishlists.user_id = authenticatedUser.id`.

3. **Product Storefront Visibility & Lifecycle:**
   - Adding products requires the product to exist and be active (`is_active = 1`).
   - If a saved product is later deactivated, the row is preserved, but marked as unavailable (`isActive: false`, `isAvailable: false`) to avoid crashing the customer UI or leaking hidden product details.

4. **Idempotent Operations:**
   - Adding an already saved product returns 200 OK (`alreadyInWishlist: true`) without creating duplicate rows (`UNIQUE (wishlist_id, product_id)`).
   - Removing an absent product returns 200 OK (`removed: false`) cleanly.

### V1 Cart Rules & Pricing Architecture

1. **One Customer = One Active Cart:**
   - Enforced by database `carts.user_id` uniqueness and status = 'active'.
   - Server helper `getOrCreateActiveCartForUser(userId)` transparently initializes a customer active cart on demand while preventing duplicate rows.
   - Operations strictly enforce `crt.user_id = ? AND crt.status = 'active'`.

2. **Server-Derived Authenticated Ownership & IDOR Protection:**
   - Identity is derived strictly from the verified session cookie via `requireUser()`.
   - Client-supplied `userId`, `cartId`, `price`, `discount`, or `totals` are completely ignored.
   - Cross-user mutations (reading, updating, or deleting another customer's cart or cart item) are strictly prevented and rejected with `404 Not Found` or `401 Unauthorized`.

3. **V1 Variant Pricing & Stock Rules (Application-Level Decision):**
   - **Product without variants:** `variantId` must be omitted/null. Price = `products.price`, stock = `products.stock_quantity`.
   - **Product with variants:** Customer must supply an active variant ID belonging to the product (`variantId` is required). Price = `product_variants.price` if present, otherwise `products.price`. Stock = `product_variants.stock_quantity`. Variant products strictly DO NOT fall back to parent product stock.
   - Active products with variants without a variant selection, or variants not belonging to the product, are rejected with client-safe `400 Bad Request`.

4. **Stock Validation on Add, Update, and Read:**
   - On `POST /api/cart/items`: `(existing_quantity + requested_quantity) <= trusted_available_stock`. Exceeding available stock is rejected with `400 Bad Request`.
   - On `PATCH /api/cart/items/:id`: `desired_final_quantity <= trusted_available_stock`.
   - On `GET /api/cart`: Current stock is inspected live and returned via `stock.available` and `stock.requestedQuantityAvailable`. Does not mutate quantity during read, but exposes availability flags so the checkout button and UI can react.
   - Inactive products in existing carts are marked `stock.available: false` and `isActive: false` without crashing.

5. **Discount Engine Integration & Decimal-Safe Totals:**
   - Reuses existing B-14 discount engine (`src/lib/server/discount.ts`).
   - Strict precedence: `Product` > `Category` > `Store-wide`.
   - No discount stacking.
   - Server recalculates authoritative totals on every operation:
     - `subtotal = sum(unitPrice × quantity)`
     - `discount = sum(lineDiscount)`
     - `shipping = 0` (default V1 storefront free shipping policy)
     - `total = subtotal - discount + shipping`
   - All monetary calculations are rounded to 2 decimal places to guarantee decimal safety.

### V1 Order Rules & Historical Snapshot Architecture

1. **Order Creation & Lifecycle:**
   - Initiated via `POST /api/orders` from the customer's authenticated active cart.
   - Newly created orders start with `status = 'pending'` and `payment_status = 'pending'`.
   - The active cart is converted (`carts.status = 'converted'`) and items cleared atomically in a single MySQL transaction.
   - Human-friendly order number generated in `DEAR-XXXXX` format with collision check against the `orders` table.

2. **Server-Authoritative Pricing & Stock:**
   - Server derives all prices, discounts, and totals from MySQL; browser-supplied prices, subtotals, discounts, and totals are completely ignored.
   - Variant pricing rules: If variant selected, explicit price used; null variant price falls back to parent product price.
   - B-14 discount engine integration: `product` > `category` > `store-wide`, strictly no stacking.
   - Stock revalidation: Every line item is validated (`requested_quantity <= available_stock`). If any item exceeds available stock, the order creation fails with `400 Bad Request` and the active cart is preserved intact.
   - **No stock decrement in B-17:** Stock is strictly validated but NOT decremented on pending order creation. Stock decrement is deferred to payment verification in B-18 so unpaid pending orders do not consume inventory.

3. **Historical Snapshots Immutability:**
   - Complete snapshot stored in `order_items` at purchase time: `product_name`, `variant_name`, `unit_price`, `quantity`, `discount_amount`, and `line_total`.
   - Complete shipping address snapshot stored in `orders`: `shipping_full_name`, `shipping_phone`, `shipping_address_line_1`, `shipping_address_line_2`, `shipping_city`, `shipping_state`, `shipping_postal_code`, `shipping_country`.
   - Subsequent changes to product names, prices, categories, deactivations, or customer profile addresses NEVER alter historical order records.

4. **Customer Ownership & IDOR Protection:**
   - Authenticated customers can only access their own orders via `GET /api/orders` and `GET /api/orders/:id`.
   - Derived strictly from session cookie (`requireUser()`). Tampering with order UUID or order number across customers yields `404 Not Found`.

5. **Founder/Admin Authorization & Management:**
   - Admin routes require `requireAdmin()`: `GET /api/admin/orders`, `GET /api/admin/orders/:id`, `PATCH /api/admin/orders/:id`.
   - Admin listing supports pagination and filtering by fulfillment status, payment status, and order number/customer search.
   - Admin status updates enforce the fulfillment state machine (`pending` → `confirmed` → `processing` → `shipped` → `delivered`, and `cancelled`).
   - Browser cannot alter order ownership or financial totals through PATCH operations.
   - **Payment Status Immutability in B-17:** Orders are created with `payment_status = 'pending'`. B-17 HTTP endpoints (`PATCH /api/admin/orders/:id` and `PATCH /api/orders/:id`) strictly disallow direct `paymentStatus` mutation. A request with only `paymentStatus` is rejected (`400 Bad Request`), and any `paymentStatus` field passed alongside fulfillment `status` is ignored. Customer PATCH requests are forbidden (`403 Forbidden`). Controlled payment transitions (`pending` → `paid` / `failed` / `refunded`) are reserved exclusively for B-18 dedicated payment verification and webhook flows.

### V1 Admin Customer Management & Suspension Architecture

1. **Full Administrative Access & Data Boundaries:**
   - Founder/admin has full permission to inspect customer business details: name, email, phone, joined date, order history, default address, and internal admin notes.
   - Authentication secrets (`password_hash`, OAuth secrets, session tokens, DB credentials) are strictly excluded from API outputs and UI representations.

2. **Persistent Status Model & Suspension:**
   - Account status stored as `status ENUM('active','suspended') NOT NULL DEFAULT 'active'` in `profiles`.
   - Admin can mutate customer `name`, `phone`, `status`, and `notes` via `PATCH /api/admin/customers/:id` (secured by `requireAdmin()`).
   - Suspension is persisted directly to MySQL; client-side fake states or sessionStorage fallbacks are strictly prohibited.

3. **Authentication Enforcement for Suspended Accounts:**
   - When a suspended customer attempts to authenticate (via email/password `/api/auth/login` or Google OAuth `/api/auth/google/callback`), login is blocked with HTTP 403 (`"Your account has been suspended. Please contact support."`) without issuing a session token.
   - Active session verification (`getCurrentUser()`, `requireUser()`) inspects customer status: if `role !== 'admin' && status === 'suspended'`, access is immediately revoked with HTTP 403.
   - Admin accounts are strictly protected from accidental suspension lockout: `role === 'admin'` accounts always retain access.

### V1 Admin Store Settings Architecture

1. **Persistent Server-Side Store Settings:**
   - Global store configurations (support email/phone, free shipping threshold, minimum order value, COD enablement, cancellation window, order notifications) persist in Hostinger MySQL table `store_settings (id=1, settings_json JSON)`.
   - Read-only UI banners and prototype mock storage are removed; settings are genuinely editable by founder/admin.

2. **API & Server Authorization:**
   - `GET /api/admin/settings`: Retrieves live store settings merged with safe defaults.
   - `PATCH /api/admin/settings`: Validates configuration payload with Zod and updates MySQL `store_settings`. Requires `requireAdmin()`. Customer access rejected with HTTP 403, unauthenticated with HTTP 401.

3. **Storefront & Checkout Consumers:**
   - Server-side order creation (`src/lib/server/order.ts`) dynamically resolves persisted store settings via `getStoreSettings()`:
     - Enforces `minimumOrderValue` before order creation.
     - Calculates shipping fees dynamically using `freeShippingThreshold` and `defaultShippingFee`.

-   Public product endpoints should return only information customers
    need.
-   Admin endpoints must require an authenticated admin session.

-   The server should derive final order totals from trusted product and

## 6. Database Requirements

The V1 database should contain the following main entities.

  Entity               Purpose
  -------------------- ------------------------------------------------
  `users/profiles`     Customer/admin profile information
  `products`           Product information and pricing
  `product_images`     References to stored product images
  `categories`         Product categories
  `product_variants`   Optional product options such as color/size

  `wishlist_items`     Products inside a wishlist

  `cart_items`         Products and quantities in a cart
  `discounts`          Discount rules and active periods
  `orders`             Customer order records
  `order_items`        Products captured in each order
  `addresses`          Delivery address information
  `payments`           Payment provider references and payment status
  `reviews`            Customer product reviews, ratings, and moderation status
  `store_settings`     Global store settings and policies (JSON configuration)

### Database Rules

-   Use unique identifiers for records.
-   Product price should be stored as a numeric money value, not as
    formatted text.
-   Orders must preserve the product price used at the time of purchase.
-   Do not rely on the current product price to reconstruct an old
    order.
-   Product deletion should normally be a soft delete/deactivation so
    existing orders remain valid.
-   Store only the minimum customer information needed for V1.

## 7. Non-Functional Requirements

Non-functional requirements describe how well the system should behave,
rather than what feature it provides.

### Performance

-   Main storefront pages should aim for a **Largest Contentful Paint
    (LCP)** of about **2.5 seconds or better** on a normal
    broadband/mobile connection.
-   Product listing pages should load without unnecessarily downloading
    full-size original images.
-   Product images should be compressed and served in appropriate
    dimensions.
-   Avoid loading large JavaScript libraries unless they solve a real V1
    requirement.
-   Database queries for common storefront pages should normally
    complete within **500 milliseconds** under expected V1 load.

### Security

-   Admin pages must require authentication.
-   Admin actions must verify authorization on the server.
-   Passwords must be hashed with bcryptjs on the server and never
    stored as plaintext.
-   Secrets must be stored in environment variables and never committed
    to the repository.
-   All production traffic must use HTTPS (encrypted web traffic).
-   Validate and sanitize user input on the server.
-   Protect against common risks such as unauthorized admin access, SQL
    injection, cross-site scripting, and forged payment callbacks.
-   Never trust client-supplied price or discount values.

### Reliability

-   Production data should use Hostinger's available daily/on-demand
    backup and restore facilities; verify the backup policy in hPanel
    before launch.
-   Payment verification must be server-side.
-   An order should not be marked as paid only because the browser says
    payment succeeded.
-   Failed payments should not create a falsely completed order.
-   Important admin changes should fail safely rather than silently
    producing partial data.

### Scalability

V1 is intended for an early-stage store with a small to moderate catalog
and initial customer traffic.

The system should comfortably support:

-   Hundreds of products
-   Hundreds to a few thousand registered customers initially
-   Normal simultaneous browsing for an early-stage store
-   Growth without immediately requiring a major architecture rewrite

Scaling beyond this should be driven by real usage data rather than
added in advance.

## 9. Security Considerations

### Authentication

Use **Dearr application authentication** for customer and admin login.

Authentication is implemented inside the Next.js server: - Email +
password accounts are stored in the `profiles` table. - Passwords are
hashed with `bcryptjs`; raw passwords are never stored. - Successful
login creates a signed, secure, HTTP-only session cookie. - Logout
clears the session cookie. - Password reset uses short-lived, single-use
reset tokens stored as hashes in MySQL.

The application should distinguish between:

-   **Customer**
-   **Admin**

A user should not become an admin merely by changing a value in the
browser.

### Authorization

Authorization means checking whether a logged-in user is allowed to
perform an action.

Examples:

-   Customer can view their own orders.
-   Customer cannot access `/admin`.
-   Admin can manage products and orders.
-   Customer cannot call admin API endpoints successfully.

### Data Protection

-   Keep payment secrets, database service keys, and other private
    credentials on the server.
-   Use HTTPS in production.
-   Do not store raw card information.
-   Store only payment-provider references required for order records.
-   Avoid logging passwords, private tokens, or sensitive payment
    information.

### Common Risks to Avoid

**1. Client-side price manipulation**

A customer could change a price in browser tools. The server must
calculate the real price.

**2. Unauthorized admin access**

Admin API routes must perform a server-side role check.

**3. Insecure product image uploads**

Validate file type/size and use controlled storage paths.

**4. Fake payment success**

Verify the payment using Razorpay's server-side verification process
before marking an order as paid.

**5. Cross-site scripting (XSS)**

Do not render untrusted user-provided content as raw HTML.

**6. SQL injection**

Use the database client's parameterized queries and avoid constructing
SQL from raw user input.

**7. Excessive information exposure**

API responses should return only the fields needed by the current user
and operation.

## 10. Environment Configuration

Production secrets should be stored in Hostinger's environment-variable
configuration and never committed to the source code.

Example configuration:

``` text
NEXT_PUBLIC_APP_URL=https://your-domain.example

DB_HOST=
DB_PORT=3306
DB_NAME=
DB_USER=
DB_PASSWORD=

SESSION_SECRET=

RAZORPAY_KEY_ID=
RAZORPAY_KEY_SECRET=
```

`DB_PASSWORD`, `SESSION_SECRET`, and `RAZORPAY_KEY_SECRET` are private
server-side values and must never be exposed to browser code.

## 17. Orders Dashboard Analytics, Abandoned Payment Cleanup & CSV Export Specification

### 17.1 Authoritative Order Placement Rule
- An online order becomes an authoritative placed order **only** after server-side payment verification (signature verification, webhook capture verification, or verified gateway payment record).
- Client redirects, browser callback URLs, or client-asserted payment status alone never mark an order placed or paid.
- Abandoned online checkout attempts (`payment_status = 'pending'` or `'failed'` without verified capture) are strictly excluded from placed order counts, order list queries, and revenue analytics.
- **Cash on Delivery (COD) Rule:** Storefront policy disables COD to prevent uncollected custom 3D printing waste. If valid COD orders exist in the database, they count as placed orders at placement, but unpaid COD orders are excluded from collected revenue until collection confirmation.

### 17.2 The Six Mutually Exclusive Dashboard Metrics
The Orders dashboard displays exactly six figures:
1. **Total Orders:** Count of eligible placed orders created within the reporting period (paid online orders + valid COD orders).
2. **Pending Dispatch:** Placed orders awaiting dispatch (`status` in `'pending'`, `'confirmed'`, `'processing'`) that are neither cancelled nor delivered.
3. **Dispatched:** Placed orders currently in transit (`status` in `'shipped'`, `'dispatched'`).
4. **Delivered:** Placed orders whose fulfillment is complete (`status = 'delivered'`).
5. **Cancelled:** Placed orders voided or cancelled (`status = 'cancelled'`). Orders cancelled after dispatch belong strictly to Cancelled, with `dispatched_at` preserved.
6. **Revenue:** Net actual collected amount (paid online payments + confirmed COD collections, minus recorded refunds) for eligible non-cancelled orders created in the reporting period.

**Mathematical Invariant:**
$$\text{Total Orders} = \text{Pending Dispatch} + \text{Dispatched} + \text{Delivered} + \text{Cancelled}$$

### 17.3 Asia/Kolkata Reporting Timezone & Half-Open Boundaries
- All period boundaries are computed in `Asia/Kolkata` (IST, UTC+05:30) using half-open intervals $[ \text{start}, \text{end} )$.
- Local midnight boundaries translate to UTC `18:30:00Z` on the preceding calendar day.
- **Five Reporting Periods:**
  - `Day`: Specific calendar date $[ \text{date } 00:00, \text{date}+1 \text{ } 00:00 )$. Defaults to Today in IST.
  - `Last Week`: Previous completed Monday 00:00:00 IST to Sunday 23:59:59.999 IST $[ \text{prevMonday}, \text{currentMonday} )$.
  - `Month`: Exact calendar month boundaries $[ \text{YYYY-MM-01}, \text{nextMonth-01} )$.
  - `Year`: Full calendar year $[ \text{YYYY-01-01}, (\text{YYYY}+1)\text{-01-01} )$.
  - `Overall`: All eligible placed orders over all time.

### 17.4 Checkout Attempt Lifecycle & Idempotent Cleanup
- Unpaid online checkout attempts expire after **30 minutes**.
- Expired attempts are retained for **30 days** for audit/investigation, then safely purged.
- Placed orders, customer records, and product inventory are never purged.
- Idempotent cleanup script: `scripts/cleanup-checkout-attempts.ts` and API `POST /api/admin/orders/cleanup`.
- Late-payment reconciliation: If a valid payment is confirmed after an attempt is marked expired, the payment is captured and reconciled idempotently without duplicate order generation.

### 17.5 Server-Streamed CSV Export & Security Protections
- Two export types: **Orders List** (`type=orders`) and **Summary** (`type=summary`), both constrained to the active reporting period.
- **Bounded-Memory Streaming:** Generated on the server via `streamOrdersListCsv` in batches of 250 rows to prevent buffering unbounded memory.
- **RFC 4180 Escaping:** Proper quoting for commas, quotes, and newlines.
- **Formula Injection Mitigation:** Prepends `'` to any untrusted text cell whose trimmed content begins with `=`, `+`, `-`, `@`. Plain numeric amounts and quantities bypass formula prefixing.
- **Encoding:** Prepends UTF-8 BOM (`\uFEFF`) ensuring Excel natively renders Indian names and the ₹ currency symbol.
- **Administrative Audit Logging:** Every export records actor ID, export type, period, date range label, row count, and outcome in `order_export_audits`. Never logs customer PII or CSV data.

## 18. Customer Delivery Address Change with Admin-Controlled Time Window Specification

### 18.1 Admin Order Policy Settings
- **Allow customers to change delivery address:** Boolean toggle (`allowAddressChange`), default `true` (ON). When disabled, hides customer UI actions and rejects server API requests.
- **Address change window:** Whole number of hours (`addressChangeWindowHours`), range 1 to 72 hours, default 6 hours.
- **Maximum address changes per order:** Positive whole number (`maxAddressChangesPerOrder`), range 1 to 10, default 2.
- **Auditing:** Every settings change records the authenticated administrator ID, timestamp, setting key, old value, and new value in `settings_audit_history` and `audit_logs`.

### 18.2 Authoritative Fixed Per-Order Deadline
- Computed and stored at order finalization: `address_edit_deadline = order_paid_at + INTERVAL window_hours HOUR`.
- Stored directly on the order record (`orders.address_edit_deadline`); not recalculated on page views.
- **Immutability:** Changing admin policy settings later applies strictly to new orders; existing order deadlines remain fixed.
- Orders created when the feature is disabled receive `NULL` deadline.
- `address_change_count` initialized to `0` for new orders.

### 18.3 Server-Side Eligibility Rules (10 Checks)
Every address-change request evaluates:
1. Global address-edit feature enabled in store settings.
2. Order has a non-null stored `address_edit_deadline`.
3. Current authoritative server time is strictly before the deadline (`now < deadline`).
4. Order is in canonical Pending Dispatch status (`pending`, `confirmed`, `processing`).
5. Order has not been dispatched (`shipped`, `dispatched`), delivered, or cancelled.
6. Permitted address changes have not been exhausted (`address_change_count < max_changes`).
7. Requester is authenticated and verified as the order owner (or authorized admin).
8. New address passes complete server-side schema and type validation.
9. Indian postal pincode is valid (6-digit, valid postal ranges 110001–855126 & 900000+, non-zero first digit).
10. Destination address maintains shipping zone invariance.

### 18.4 Concurrency & Row-Level Locking
- Address modifications and dispatch transitions execute inside MySQL transactions using `SELECT ... FOR UPDATE` row locks on the order.
- If dispatch wins the race, address modification is rejected with `order_dispatched`.
- If address modification commits first, dispatch observes and uses the updated address.
- History insertion, address update, and counter increment occur atomically.

### 18.5 Audit Trail & Rate Limiting
- `order_address_history` records snapshot of old and new addresses, actor role (`customer` | `admin`), actor ID, requester IP, and UTC timestamp.
- Client responses mask private IP addresses and sensitive audit details.
- Distributed rate limiting via `rate_limits` table enforces a maximum of 5 attempts per 15-minute rolling window per user/IP.

### 18.6 Orders List CSV Export
- Extended with `address_changed` column (`yes` if `address_change_count > 0`, else `no`).
- Exports the latest updated shipping address while preserving RFC 4180 escaping and formula injection protections.

## 19. Cart Abandonment Recovery, Feedback, Alternatives, and Future Automation Groundwork Specification

### 19.1 Abandonment Detection & Payment Failure Tracking
- **Authenticated Account Customers Only:** Checkout, recovery sheet, alternative swaps, feedback, and notification consent are strictly scoped to authenticated customers via session verification (`requireUser()`). Guest checkout is explicitly not supported.
- **Authoritative Attempt Lifecycle:** Checkout attempts transition to `'abandoned'` on modal dismissal and `'failed'` on payment failures with sanitized gateway codes/descriptions.
- **Unpaid Isolation Invariant:** Unpaid checkout attempts are strictly isolated from `orders`. Unpaid attempts never count in revenue, placed order counts, or order items.
- **Authoritative Reconciliation:** Recovery presentation checks orders and payments; paid attempts are suppressed and routed to order confirmation.
- **Extended Retention & Cleanup:** Abandoned and failed attempts receive an extended 90-day retention window (`retention_until = NOW() + INTERVAL 90 DAY`). Idempotent cleanup script `scripts/cleanup-checkout-attempts.ts` and `POST /api/admin/orders/cleanup` purge expired records beyond retention window without mutating placed orders.

### 19.2 Responsive Customer Recovery Sheet
- **Modal Dismissal Drawer:** Displays "Your cart is saved" reassurance, cart items, order total, and primary "Retry payment" action (launching a fresh checkout attempt).
- **Single Presentation Guard:** The recovery sheet is shown at most once for the same checkout attempt (`recovery_shown_at` timestamp tracking).
- **Payment Failure Diagnostics:** Explains customer-friendly failure reasons with clear retry options.
- **Direct Alternatives:** Option to view and swap in lower-priced items from the same category.
- **Multi-Select Feedback:** Quick-tap reasons for leaving with optional comment.
- **Notification Consent:** Explicit, unchecked consent checkboxes for future recovery channels.

### 19.3 Lower-Priced Alternatives Query & Server-Side Cart Item Swap
- **Eligibility Criteria:** Same category, active (`is_active = 1`), in-stock (`stock_quantity > 0`), not already in cart, strictly lower unit price than current cart item.
- **Color Selection:** Matches color variant by name/slug/hex if available, falling back to first available in-stock color.
- **Full-Quantity Preservation:** Swapping into an alternative preserves the exact full quantity and valid color selection of the original cart item.
- **Atomic Swap Transaction:** Executes within MySQL transaction: deletes old cart item, inserts new alternative cart item, logs internal swap event.
- **Concurrency & Price Protection:** Validates live stock and price; aborts with HTTP 409 Conflict if stock is exhausted or price changed stale, leaving original cart items unchanged.

### 19.4 Checkout Feedback Model & Rate Limiting
- **Normalized Schema:** `checkout_feedback` captures validated reasons array, optional sanitized comment (max 500 characters), and skip state. Exclusively associated with authenticated user profiles.
- **Duplicate Prevention:** Exactly one submission or skip is persisted per checkout attempt; subsequent submissions for the same attempt are rejected with 409 Conflict.
- **Rate Limiting:** Enforced via `rate_limits` table: maximum 10 feedback submissions per 15-minute rolling window per IP.

### 19.5 Future Automation Groundwork (Strictly Data-Only)
- **Zero Notification Policy:** Strictly data-only groundwork in this phase. Zero outbound SMS, WhatsApp, or emails are dispatched, and no external messaging provider APIs are invoked.
- **Explicit Consent Storage:** Checkboxes remain unchecked by default; records channel (`email`, `whatsapp`, `sms`), contact value, exact displayed consent text ("I agree to receive price-drop alerts and cart updates from Dearr."), IP, timestamp, and 90-day retention window.
- **Rightful Withdrawal:** Allows the authenticated customer to withdraw consent at any time via `POST /api/notifications/unsubscribe`, updating `is_withdrawn = 1` and recording `withdrawn_at`.

### 19.6 Price History & Internal Telemetry Events
- **Price History Auditing:** `product_price_history` records previous price, new price, and current price for products and individual color variants upon catalog updates.
- **Internal Events Store:** `internal_events` captures 12 funnel event types: checkout initiated, modal dismissed, payment failed, recovery shown, alternatives viewed, item swapped, feedback submitted, feedback skipped, consent recorded/unsubscribed, and cleanup executed.

### 19.7 Protected Admin Abandonment Analytics & CSV Export
- **Reporting Periods:** Synchronized with Asia/Kolkata half-open intervals $[ \text{start}, \text{end} )$ (Day, Last Week, Month, Year, Overall).
- **Authoritative KPI Metric Definitions:**
  - `Initiated Checkouts`: Total checkout attempts created in the period.
  - `Abandoned Checkouts & Rate %`: Attempts marked abandoned or expired / initiated checkouts * 100.
  - `Payment Failures`: Attempts in 'failed' status with gateway errors.
  - `Recovery Impressions`: Distinct attempts where `recovery_shown_at` was recorded.
  - `Recovered Orders & Rate %`: Placed orders converted from an attempt where recovery was shown or retry was clicked / total unpaid attempts * 100.
  - `At-Risk & Recovered Revenue`: Amount from unpaid attempts vs amount converted to verified orders.
- **Top Reasons Breakdown:** Aggregated multi-select checkout feedback percentages and counts.
- **Streamed CSV Export:** `GET /api/admin/abandonment/export` with RFC 4180 escaping, formula injection mitigation (`'`), UTF-8 BOM, and admin audit logging in `order_export_audits`.

### 19.8 Admin Recovery Settings
- Controls in Admin Settings Section G: `recoverySheetEnabled`, `alternativesEnabled`, `maxAlternatives` (1-4), `feedbackEnabled`, and customizable feedback reasons list.
