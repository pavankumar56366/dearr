# Dearr --- Technical Requirements Document (TRD)

> **V1 infrastructure:** Hostinger (Node.js hosting + MySQL + file
> storage) with Dearr application authentication.

**Version:** V1\
**Product:** Dearr E-commerce Website\
**Audience:** Beginner developers building with Antigravity\
**Related Document:** `Dearr_PRD.md`

------------------------------------------------------------------------

## 1. Overview

Dearr V1 will be a single web application containing two connected
experiences: a customer-facing e-commerce storefront and a protected
founder/admin dashboard. The application will support product browsing,
search, categories, product details, wishlist, cart, checkout, customer
accounts, order creation, and basic order management. The admin side
will let the founder add and edit products, manage categories and
discounts, and view/update orders. To keep V1 beginner-friendly and
avoid unnecessary complexity, the application should use one main web
codebase, Hostinger MySQL for application data, application-managed
authentication, Hostinger file storage for product images, and a hosted
payment provider instead of a separate backend server or microservices.

### Architecture Explanation

There is one main Dearr web application.

- **Customer pages** handle browsing and shopping.
- **Admin pages** handle store management.
- **Next.js Route Handlers** perform sensitive operations on the server.
- **Hostinger** provides the Node.js runtime, MySQL database, and persistent file storage; Dearr implements authentication and authorization in the application.
- **Razorpay** handles payment processing.
- The frontend should never receive secret credentials such as a database service key or payment secret.

### Important rule

The browser must not be trusted to decide the final price, discount,
stock quantity, or payment status. The server must recalculate or verify
these values using trusted database/payment-provider information.

### V1 Discount Rules & Precedence

1. **Supported Scopes (3 scopes):**
   - `Store-wide` (`store`): Applies to all eligible products in the store.
   - `Category-wise` (`category`): Applies to all products belonging to the selected category.
   - `Specific Product` (`product`): Applies exclusively to the targeted product.

2. **Precedence Hierarchy:**
   When a product matches multiple active discounts, Dearr V1 applies strict priority:
   `Specific Product` > `Category-wise` > `Store-wide`

3. **No Discount Stacking:**
   Discounts are strictly never stacked or summed together. Exactly one applicable discount is resolved per product context.

4. **Same-Priority Conflict Prevention:**
   Creating or updating active/scheduled discounts that target the same scope/entity across an overlapping time period is prohibited and rejected with `409 Conflict`.

### V1 Wishlist Rules & Ownership Architecture

1. **One Customer = One Wishlist:**
   - Enforced by database `UNIQUE (user_id)` constraint on `wishlists`.
   - Server helper `getOrCreateWishlistForUser(userId)` transparently initializes a customer wishlist on demand while preventing duplicate rows.

2. **Server-Derived Authenticated Ownership:**
   - Identity is derived strictly from the verified session cookie via `requireUser()`.
   - Never trusts client-supplied `userId` or `wishlistId` (prevents IDOR vulnerabilities).
   - All read/write queries join `wishlists` and filter by `wishlists.user_id = authenticatedUser.id`.

3. **Product Storefront Visibility & Lifecycle:**
   - Adding products requires the product to exist and be active (`is_active = 1`).
   - If a saved product is later deactivated, the row is preserved, but marked as unavailable (`isActive: false`, `isAvailable: false`) to avoid crashing the customer UI or leaking hidden product details.

4. **Idempotent Operations:**
   - Adding an already saved product returns 200 OK (`alreadyInWishlist: true`) without creating duplicate rows (`UNIQUE (wishlist_id, product_id)`).
   - Removing an absent product returns 200 OK (`removed: false`) cleanly.

### V1 Cart Rules & Pricing Architecture

1. **One Customer = One Active Cart:**
   - Enforced by database `carts.user_id` uniqueness and status = 'active'.
   - Server helper `getOrCreateActiveCartForUser(userId)` transparently initializes a customer active cart on demand while preventing duplicate rows.
   - Operations strictly enforce `crt.user_id = ? AND crt.status = 'active'`.

2. **Server-Derived Authenticated Ownership & IDOR Protection:**
   - Identity is derived strictly from the verified session cookie via `requireUser()`.
   - Client-supplied `userId`, `cartId`, `price`, `discount`, or `totals` are completely ignored.
   - Cross-user mutations (reading, updating, or deleting another customer's cart or cart item) are strictly prevented and rejected with `404 Not Found` or `401 Unauthorized`.

3. **V1 Variant Pricing & Stock Rules (Application-Level Decision):**
   - **Product without variants:** `variantId` must be omitted/null. Price = `products.price`, stock = `products.stock_quantity`.
   - **Product with variants:** Customer must supply an active variant ID belonging to the product (`variantId` is required). Price = `product_variants.price` if present, otherwise `products.price`. Stock = `product_variants.stock_quantity`. Variant products strictly DO NOT fall back to parent product stock.
   - Active products with variants without a variant selection, or variants not belonging to the product, are rejected with client-safe `400 Bad Request`.

4. **Stock Validation on Add, Update, and Read:**
   - On `POST /api/cart/items`: `(existing_quantity + requested_quantity) <= trusted_available_stock`. Exceeding available stock is rejected with `400 Bad Request`.
   - On `PATCH /api/cart/items/:id`: `desired_final_quantity <= trusted_available_stock`.
   - On `GET /api/cart`: Current stock is inspected live and returned via `stock.available` and `stock.requestedQuantityAvailable`. Does not mutate quantity during read, but exposes availability flags so the checkout button and UI can react.
   - Inactive products in existing carts are marked `stock.available: false` and `isActive: false` without crashing.

5. **Discount Engine Integration & Decimal-Safe Totals:**
   - Reuses existing B-14 discount engine (`src/lib/server/discount.ts`).
   - Strict precedence: `Product` > `Category` > `Store-wide`.
   - No discount stacking.
   - Server recalculates authoritative totals on every operation:
     - `subtotal = sum(unitPrice × quantity)`
     - `discount = sum(lineDiscount)`
     - `shipping = 0` (default V1 storefront free shipping policy)
     - `total = subtotal - discount + shipping`
   - All monetary calculations are rounded to 2 decimal places to guarantee decimal safety.

### V1 Order Rules & Historical Snapshot Architecture

1. **Order Creation & Lifecycle:**
   - Initiated via `POST /api/orders` from the customer's authenticated active cart.
   - Newly created orders start with `status = 'pending'` and `payment_status = 'pending'`.
   - The active cart is converted (`carts.status = 'converted'`) and items cleared atomically in a single MySQL transaction.
   - Human-friendly order number generated in `DEAR-XXXXX` format with collision check against the `orders` table.

2. **Server-Authoritative Pricing & Stock:**
   - Server derives all prices, discounts, and totals from MySQL; browser-supplied prices, subtotals, discounts, and totals are completely ignored.
   - Variant pricing rules: If variant selected, explicit price used; null variant price falls back to parent product price.
   - B-14 discount engine integration: `product` > `category` > `store-wide`, strictly no stacking.
   - Stock revalidation: Every line item is validated (`requested_quantity <= available_stock`). If any item exceeds available stock, the order creation fails with `400 Bad Request` and the active cart is preserved intact.
   - **No stock decrement in B-17:** Stock is strictly validated but NOT decremented on pending order creation. Stock decrement is deferred to payment verification in B-18 so unpaid pending orders do not consume inventory.

3. **Historical Snapshots Immutability:**
   - Complete snapshot stored in `order_items` at purchase time: `product_name`, `variant_name`, `unit_price`, `quantity`, `discount_amount`, and `line_total`.
   - Complete shipping address snapshot stored in `orders`: `shipping_full_name`, `shipping_phone`, `shipping_address_line_1`, `shipping_address_line_2`, `shipping_city`, `shipping_state`, `shipping_postal_code`, `shipping_country`.
   - Subsequent changes to product names, prices, categories, deactivations, or customer profile addresses NEVER alter historical order records.

4. **Customer Ownership & IDOR Protection:**
   - Authenticated customers can only access their own orders via `GET /api/orders` and `GET /api/orders/:id`.
   - Derived strictly from session cookie (`requireUser()`). Tampering with order UUID or order number across customers yields `404 Not Found`.

5. **Founder/Admin Authorization & Management:**
   - Admin routes require `requireAdmin()`: `GET /api/admin/orders`, `GET /api/admin/orders/:id`, `PATCH /api/admin/orders/:id`.
   - Admin listing supports pagination and filtering by fulfillment status, payment status, and order number/customer search.
   - Admin status updates enforce the fulfillment state machine (`pending` → `confirmed` → `processing` → `shipped` → `delivered`, and `cancelled`).
   - Browser cannot alter order ownership or financial totals through PATCH operations.
   - **Payment Status Immutability in B-17:** Orders are created with `payment_status = 'pending'`. B-17 HTTP endpoints (`PATCH /api/admin/orders/:id` and `PATCH /api/orders/:id`) strictly disallow direct `paymentStatus` mutation. A request with only `paymentStatus` is rejected (`400 Bad Request`), and any `paymentStatus` field passed alongside fulfillment `status` is ignored. Customer PATCH requests are forbidden (`403 Forbidden`). Controlled payment transitions (`pending` → `paid` / `failed` / `refunded`) are reserved exclusively for B-18 dedicated payment verification and webhook flows.

## 6. Database Requirements

The V1 database should contain the following main entities.

  Entity               Purpose
  -------------------- ------------------------------------------------
  `users/profiles`     Customer/admin profile information
  `products`           Product information and pricing
  `product_images`     References to stored product images
  `categories`         Product categories
  `product_variants`   Optional product options such as color/size
  `wishlists`          Saved products for customers
  `wishlist_items`     Products inside a wishlist
  `carts`              Customer or guest cart
  `cart_items`         Products and quantities in a cart
  `discounts`          Discount rules and active periods
  `orders`             Customer order records
  `order_items`        Products captured in each order
  `addresses`          Delivery address information
  `payments`           Payment provider references and payment status

### Database Rules

-   Use unique identifiers for records.
-   Product price should be stored as a numeric money value, not as
    formatted text.
-   Orders must preserve the product price used at the time of purchase.
-   Do not rely on the current product price to reconstruct an old
    order.
-   Product deletion should normally be a soft delete/deactivation so
    existing orders remain valid.
-   Store only the minimum customer information needed for V1.

## 7. Non-Functional Requirements

Non-functional requirements describe how well the system should behave,
rather than what feature it provides.

### Performance

-   Main storefront pages should aim for a **Largest Contentful Paint
    (LCP)** of about **2.5 seconds or better** on a normal
    broadband/mobile connection.
-   Product listing pages should load without unnecessarily downloading
    full-size original images.
-   Product images should be compressed and served in appropriate
    dimensions.
-   Avoid loading large JavaScript libraries unless they solve a real V1
    requirement.
-   Database queries for common storefront pages should normally
    complete within **500 milliseconds** under expected V1 load.

### Security

-   Admin pages must require authentication.
-   Admin actions must verify authorization on the server.
-   Passwords must be hashed with bcryptjs on the server and never
    stored as plaintext.
-   Secrets must be stored in environment variables and never committed
    to the repository.
-   All production traffic must use HTTPS (encrypted web traffic).
-   Validate and sanitize user input on the server.
-   Protect against common risks such as unauthorized admin access, SQL
    injection, cross-site scripting, and forged payment callbacks.
-   Never trust client-supplied price or discount values.

### Reliability

-   Production data should use Hostinger's available daily/on-demand
    backup and restore facilities; verify the backup policy in hPanel
    before launch.
-   Payment verification must be server-side.
-   An order should not be marked as paid only because the browser says
    payment succeeded.
-   Failed payments should not create a falsely completed order.
-   Important admin changes should fail safely rather than silently
    producing partial data.

### Scalability

V1 is intended for an early-stage store with a small to moderate catalog
and initial customer traffic.

The system should comfortably support:

-   Hundreds of products
-   Hundreds to a few thousand registered customers initially
-   Normal simultaneous browsing for an early-stage store
-   Growth without immediately requiring a major architecture rewrite

Scaling beyond this should be driven by real usage data rather than
added in advance.

## 9. Security Considerations

### Authentication

Use **Dearr application authentication** for customer and admin login.

Authentication is implemented inside the Next.js server: - Email +
password accounts are stored in the `profiles` table. - Passwords are
hashed with `bcryptjs`; raw passwords are never stored. - Successful
login creates a signed, secure, HTTP-only session cookie. - Logout
clears the session cookie. - Password reset uses short-lived, single-use
reset tokens stored as hashes in MySQL.

The application should distinguish between:

-   **Customer**
-   **Admin**

A user should not become an admin merely by changing a value in the
browser.

### Authorization

Authorization means checking whether a logged-in user is allowed to
perform an action.

Examples:

-   Customer can view their own orders.
-   Customer cannot access `/admin`.
-   Admin can manage products and orders.
-   Customer cannot call admin API endpoints successfully.

### Data Protection

-   Keep payment secrets, database service keys, and other private
    credentials on the server.
-   Use HTTPS in production.
-   Do not store raw card information.
-   Store only payment-provider references required for order records.
-   Avoid logging passwords, private tokens, or sensitive payment
    information.

### Common Risks to Avoid

**1. Client-side price manipulation**

A customer could change a price in browser tools. The server must
calculate the real price.

**2. Unauthorized admin access**

Admin API routes must perform a server-side role check.

**3. Insecure product image uploads**

Validate file type/size and use controlled storage paths.

**4. Fake payment success**

Verify the payment using Razorpay's server-side verification process
before marking an order as paid.

**5. Cross-site scripting (XSS)**

Do not render untrusted user-provided content as raw HTML.

**6. SQL injection**

Use the database client's parameterized queries and avoid constructing
SQL from raw user input.

**7. Excessive information exposure**

API responses should return only the fields needed by the current user
and operation.

## 10. Environment Configuration

Production secrets should be stored in Hostinger's environment-variable
configuration and never committed to the source code.

Example configuration:

``` text
NEXT_PUBLIC_APP_URL=https://your-domain.example

DB_HOST=
DB_PORT=3306
DB_NAME=
DB_USER=
DB_PASSWORD=

SESSION_SECRET=

RAZORPAY_KEY_ID=
RAZORPAY_KEY_SECRET=
```

`DB_PASSWORD`, `SESSION_SECRET`, and `RAZORPAY_KEY_SECRET` are private
server-side values and must never be exposed to browser code.

## 12. Development Rules for V1

1.  Keep customer and admin functionality in the same application but
    clearly separated.
2.  Build core shopping flows before optional features.
3.  Reuse shared UI components instead of creating visually different
    versions of the same element.
4.  Keep the Dearr color palette centralized and consistent.
5.  Never put secrets in client-side code.
6.  Never trust the browser for price, stock, discount, or payment
    status.
7.  Update documentation when a major technical decision changes.
8.  Do not add a new service when an existing V1 service can handle the
    requirement.
9.  Test the complete flow after changes: browse → product → cart →
    checkout → order.
10. Test admin changes by checking that the storefront reflects the
    updated data.

## 13. Assumptions & Open Technical Questions

### Assumptions

-   Dearr is launching as a single-store e-commerce website.
-   V1 will initially serve an India-focused customer base.
-   Product images will be supplied by the Dearr team.
-   Hostinger is acceptable as the managed database/auth/storage
    platform.
-   Next.js is acceptable as the main application framework.
-   The founder/admin dashboard is part of the same application.
-   The initial store traffic is relatively small.

### Open Technical Questions

1.  Should customers be allowed to checkout as guests, or must they
    create an account?
2.  Which payment provider will Dearr officially use at launch?
3.  Which delivery/shipping provider, if any, will be integrated in V1?
4.  Will products require variants such as color, size, or material?
5.  Should the cart work for guests before login?
6.  What exact order statuses should the admin dashboard support?
7.  Should discounts support percentage, fixed amount, product-specific,
    category-specific, and store-wide rules?

## 14. V1 Technical Success Condition

The V1 technical implementation is considered ready when:

-   A customer can browse and search active products.
-   A customer can view product details.
-   A customer can use wishlist and cart functionality.
-   A customer can complete the checkout/payment flow.
-   A valid order is stored correctly after payment verification.
-   A founder/admin can securely log in.
-   A founder/admin can add, edit, activate/deactivate products.
-   A founder/admin can manage basic discounts.
-   A founder/admin can view and update orders.
-   Changes made through the admin dashboard appear correctly on the
    storefront.
-   The application works on both desktop and mobile screen sizes.
-   No production secrets are exposed in client-side code.

## 15. V1 Architecture Principle

**Prefer one simple, well-documented application over many separate
systems.**

The first release should be easy for a beginner developer to understand,
easy for the founder to operate, and structured so later V2 features can
be added without rebuilding the entire product.
