# Dearr --- Application Flow (APPFLOW)

**Version:** V1\
**Product:** Dearr E-commerce Website\
**Platform:** Web\
**User Types:** Customer, Founder/Admin\
**Related Documents:** `Dearr_PRD.md`, `Dearr_TRD.md`

This product/flow/design document is provider-agnostic. V1

## 1. Screen Inventory

### Customer Screens

  -----------------------------------------------------------------------
  Screen                              Purpose
  ----------------------------------- -----------------------------------

  **Cart**                            Reviews selected products,
                                      quantities, discounts, and total.

## 2. Entry Points

### Customer Entry Points

1.  **Direct website URL**
    -   Open → Home
2.  **Shared product link**
    -   Open product URL → Product Details
3.  **Shared category link**
    -   Open category URL → Category Products
4.  **Search engine result**
    -   Open indexed product/category/page → Relevant page
5.  **Navigation**
    -   Home → Shop / Category / Wishlist / Cart / Login
6.  **Promotional banner or featured product**
    -   Home → Product Details or relevant Category
7.  **Returning customer**
    -   Open website → Home
    -   Or open saved product/order/account link → Relevant page
8.  **Login-required action**
    -   Attempt Wishlist/Account action → Login → Return to original
        action/page after successful login
9.  **Order link**
    -   Customer opens order-related link → Login if required → Order
        Details

### Admin Entry Points

1.  **Admin URL**
    -   Open `/admin` → Admin Login or Dashboard depending on session
2.  **Existing admin session**
    -   Open `/admin` → Dashboard
3.  **Expired admin session**
    -   Admin page → Admin Login → Dashboard after successful login

``` text

  ↓
Discounts
  ↓
Add Discount
  ↓
Enter Discount Details
  ↓

  ↓
Set Start & End Date
  ↓

  ↓

  ↓

  ↓
```

### 3.4 Founder Updates an Order

``` text
Admin
 ↓
GET /api/admin/orders
 ↓
Order list
 ↓
GET /api/admin/orders/:id
 ↓
PATCH /api/admin/orders/:id
 ↓
Updated fulfillment status (pending → confirmed → processing → shipped → delivered)
 ↓
Customer reads updated status in My Orders / Order Details
```

> **B-17 Scope & Security Note:** `PATCH /api/admin/orders/:id` only modifies fulfillment `status` or processes cancellations. Orders are created with `payment_status = 'pending'`. Direct `paymentStatus` mutation is strictly blocked across both admin and customer HTTP endpoints. Controlled transitions of `payment_status` (pending → paid / failed / refunded) belong exclusively to B-18 dedicated payment verification and webhook processing.

### 3.5 Server-Authoritative Order Creation Flow (B-17)

``` text
CUSTOMER CHECKOUT
       ↓
POST /api/orders
       ↓
Authenticate customer (requireUser)
       ↓
Resolve current active cart
       ↓
Revalidate products / variants / stock
       ↓
Recalculate trusted pricing (MySQL catalog)
       ↓
Resolve B-14 discounts (Product > Category > Store-wide, no stacking)
       ↓
Calculate server totals (subtotal - discount + shipping)
       ↓
Create pending order + item snapshots (order_number: DEAR-XXXXX, status: pending, payment_status: pending)
       ↓
Convert/clear active cart (status = 'converted', cart_items deleted)
       ↓
Return order record
       ↓
Order Confirmation (/order-confirmed?orderNumber=DEAR-XXXXX)
       ↓
Customer Order Details (/account/orders/:orderNumber via GET /api/orders/:id)
```

### 3.6 Founder Manages Customers

``` text
Admin UI (/admin/customers)

GET /api/admin/customers (guarded by requireAdmin)

Customer repository (joins profiles, orders metrics, addresses)

Hostinger MySQL
 ↓
View / Edit Customer (/admin/customers/[id] & /admin/customers/[id]/edit)
 ↓
PATCH /api/admin/customers/[id] (status: active/inactive/blocked, notes)
```

### 3.7 Founder Moderates Customer Reviews

``` text
Reviews repository (joins reviews, products, product_images)
```

### 3.8 Founder Inspects Store Settings

### 4.6 Cart Management

``` text
Customer
  ↓
Add to Cart (Product Page / Shop Card / Wishlist)
  ↓
Authentication Check
  ├── Authenticated Customer:
  │     ↓
  │   POST /api/cart/items (productId, variantId?, quantity)
  │     ↓
  │   Server validates product exists, is_active=1
  │   Server validates variant exists & belongs to product if variants present
  │   Server validates stock: (existing_qty + added_qty) <= current_stock
  │     ↓
  │   Saved to MySQL (carts + cart_items)
  │     ↓
  │   GET /api/cart calculates trusted prices + B-14 discounts + server totals
  │     ↓
  │   Cart UI & Header Badge synchronized with authoritative server state
  │
  └── Guest / Visitor:
        ↓
      Preserves existing demo/sessionStorage fallback (no broken UI)
```

``` text
Cart Screen (/cart)
  ↓
GET /api/cart (Authenticated)
  ├── Empty Cart → Show Empty State + "Start Shopping" button
  └── Has Items:
        ├── Increase Quantity (+) → PATCH /api/cart/items/:id (finalQty) → Server re-validates stock → Recalculates Totals
        ├── Decrease Quantity (-) → PATCH /api/cart/items/:id (finalQty) → Server re-validates stock → Recalculates Totals
        ├── Remove Item (Trash)   → DELETE /api/cart/items/:id → Removes row from MySQL → Recalculates Totals
        ├── Stock Changed Alert   → Server returns available: false / requestedQuantityAvailable: false → UI alerts customer
        ├── Inactive Product      → Marked unavailable safely without server crash
        ├── Continue Shopping     → Navigate back to /shop
        └── Proceed to Checkout   → Validates all items available → Navigate to /checkout
```

## 8. Navigation Rules

### Customer

-   The Dearr logo always returns to **Home**.
-   Main navigation should always provide access to **Shop**,
    **Search**, **Wishlist**, **Cart**, and **Account/Login** as
    appropriate.
-   From any product-related screen, the customer should have a clear
    way to continue shopping.
-   Checkout should always provide a safe way to return to the cart
    before payment.
-   A successful order should never end in a dead-end; the customer can
    view order details or continue shopping.

### Admin

-   Every admin screen should provide access back to the **Admin
    Dashboard** or the relevant section list.
-   Forms should have clear **Save** and **Cancel/Back** actions.
-   Destructive actions such as delete/deactivate should require
    confirmation.
-   Admin errors should preserve form input where possible.
-   Expired authentication should return the admin to **Admin Login**,
    then back to the requested page after successful authentication.

## 9. V1 Flow Principles

1.  **No dead ends:** Every screen has at least one useful next action.
2.  **One clear primary action:** Each important screen should have an
    obvious main CTA (Call to Action).
3.  **Short shopping path:** Browse → Product → Cart → Checkout →
    Payment → Confirmation.
4.  **Safe recovery:** Errors should explain what happened and provide a
    next step.
5.  **Admin simplicity:** Common founder tasks should take as few
    screens as practical.
6.  **Consistent navigation:** Customer and admin navigation should
    remain predictable.
7.  **Protect user input:** Failed requests should not unnecessarily
    clear forms or carts.
8.  **Server-trusted decisions:** Price, discount, stock, and payment
    outcomes must be verified by the application rather than trusted
    from browser input.

## 11. V1 End-to-End Principle

The complete Dearr V1 should always guide the user toward one of three
useful outcomes:

``` text
Customer
→ Discover a product
→ Purchase a product
→ Save a product for later
→ Manage an existing order
→ Or safely recover from an error

Admin
→ Manage products
→ Manage discounts
→ Manage categories
→ Manage orders
→ Or safely recover from an admin error
```

**Core principle:** Every flow should be understandable to a first-time
user, and every failure state should provide a clear way forward.
