## 1. Screen Inventory

### Customer Screens

  -----------------------------------------------------------------------
  Screen                              Purpose
  ----------------------------------- -----------------------------------
  **Home**                            Introduces Dearr, highlights
                                      products/categories/offers, and
                                      starts shopping.

  **Shop / All Products**             Shows the complete active product

  **Category Products**               Shows products belonging to one
                                      selected category.

  **Product Details**                 Provides complete information and
                                      purchase actions for one product.

  **Wishlist**                        Shows products saved by the
                                      customer for later.

  **Cart**                            Reviews selected products,
                                      quantities, discounts, and total.

  **Checkout**                        Collects delivery details and
                                      prepares the order for payment.

  **Payment**                         Handles the payment step through
                                      the selected payment provider.

  **Order Confirmation**              Confirms a successfully placed
                                      order and shows basic order
                                      information.

  **Login**                           Lets an existing customer sign in.

  **Signup**                          Lets a new customer create an
                                      account.

  **Forgot Password**                 Starts password recovery.

  **Reset Password**                  Lets the customer create a new
                                      password after recovery
                                      verification.

  **Account**                         Shows basic customer account
                                      information and order access.

  **My Orders**                       Shows the customer's
                                      previous/current orders.

  **Order Details**                   Shows one order's items, amount,

  **404 / Not Found**                 Handles invalid or removed URLs and
                                      provides a route back to shopping.

  Unavailable**                       application/server problems and

## 2. Entry Points

### Customer Entry Points

1.  **Direct website URL**
    -   Open → Home
2.  **Shared product link**
    -   Open product URL → Product Details
3.  **Shared category link**
    -   Open category URL → Category Products
4.  **Search engine result**
    -   Open indexed product/category/page → Relevant page
5.  **Navigation**
    -   Home → Shop / Category / Wishlist / Cart / Login
6.  **Promotional banner or featured product**
    -   Home → Product Details or relevant Category
7.  **Returning customer**
    -   Open website → Home
    -   Or open saved product/order/account link → Relevant page
8.  **Login-required action**
    -   Attempt Wishlist/Account action → Login → Return to original
        action/page after successful login
9.  **Order link**
    -   Customer opens order-related link → Login if required → Order
        Details

### Admin Entry Points

1.  **Admin URL**
    -   Open `/admin` → Admin Login or Dashboard depending on session
2.  **Existing admin session**
    -   Open `/admin` → Dashboard
3.  **Expired admin session**
    -   Admin page → Admin Login → Dashboard after successful login

``` text

  ↓
Discounts
  ↓
Add Discount

  ↓

  ↓
Set Start & End Date
  ↓

  ↓
Validation Successful

  ↓

  ↓
```

### 3.4 Founder Updates an Order

``` text
Admin
 ↓
GET /api/admin/orders
 ↓
Order list
 ↓
GET /api/admin/orders/:id
 ↓
PATCH /api/admin/orders/:id
 ↓
Updated fulfillment status (pending → confirmed → processing → shipped → delivered)
 ↓
Customer reads updated status in My Orders / Order Details
```

> **B-17 Scope & Security Note:** `PATCH /api/admin/orders/:id` only modifies fulfillment `status` or processes cancellations. Orders are created with `payment_status = 'pending'`. Direct `paymentStatus` mutation is strictly blocked across both admin and customer HTTP endpoints. Controlled transitions of `payment_status` (pending → paid / failed / refunded) belong exclusively to B-18 dedicated payment verification and webhook processing.

### 3.5 Server-Authoritative Order Creation Flow (B-17)

``` text
CUSTOMER CHECKOUT
       ↓
POST /api/orders
       ↓
Authenticate customer (requireUser)
       ↓
Resolve current active cart
       ↓
Revalidate products / variants / stock
       ↓
Recalculate trusted pricing (MySQL catalog)
       ↓
Resolve B-14 discounts (Product > Category > Store-wide, no stacking)
       ↓
Calculate server totals (subtotal - discount + shipping)
       ↓
Create pending order + item snapshots (order_number: DEAR-XXXXX, status: pending, payment_status: pending)
       ↓
Convert/clear active cart (status = 'converted', cart_items deleted)
       ↓
Return order record
       ↓
Order Confirmation (/order-confirmed?orderNumber=DEAR-XXXXX)
       ↓
Customer Order Details (/account/orders/:orderNumber via GET /api/orders/:id)
```

### 3.6 Founder Manages Customers

``` text
Admin UI (/admin/customers)
 ↓
GET /api/admin/customers (guarded by requireAdmin)
 ↓
Customer repository (joins profiles, orders metrics, addresses)
 ↓
Hostinger MySQL
 ↓
View / Edit Customer (/admin/customers/[id] & /admin/customers/[id]/edit)
 ↓
PATCH /api/admin/customers/[id] (status: active/inactive/blocked, notes)
```

### 3.7 Founder Moderates Customer Reviews

``` text
Admin UI (/admin/reviews)
 ↓
GET /api/admin/reviews (guarded by requireAdmin)
 ↓
Reviews repository (joins reviews, products, product_images)
 ↓
Hostinger MySQL
 ↓
Review Moderation Queue (/admin/reviews/[id])
 ↓
PATCH /api/admin/reviews/[id] (status: pending/approved/rejected/flagged, adminNote)
```

### 3.8 Founder Inspects Store Settings

``` text

 ↓
GET /api/admin/settings (guarded by requireAdmin)
 ↓
Safe store configuration (no secrets exposed)
```

### 4.6 Cart Management

``` text
Customer
  ↓
Add to Cart (Product Page / Shop Card / Wishlist)
  ↓
Authentication Check
  ├── Authenticated Customer:
  │     ↓
  │   POST /api/cart/items (productId, variantId?, quantity)
  │     ↓
  │   Server validates product exists, is_active=1
  │   Server validates variant exists & belongs to product if variants present
  │   Server validates stock: (existing_qty + added_qty) <= current_stock
  │     ↓
  │   Saved to MySQL (carts + cart_items)
  │     ↓
  │   GET /api/cart calculates trusted prices + B-14 discounts + server totals
  │     ↓
  │   Cart UI & Header Badge synchronized with authoritative server state
  │
  └── Guest / Visitor:
        ↓
      Preserves existing demo/sessionStorage fallback (no broken UI)
```

``` text
Cart Screen (/cart)
  ↓
GET /api/cart (Authenticated)
  ├── Empty Cart → Show Empty State + "Start Shopping" button
  └── Has Items:
        ├── Increase Quantity (+) → PATCH /api/cart/items/:id (finalQty) → Server re-validates stock → Recalculates Totals
        ├── Decrease Quantity (-) → PATCH /api/cart/items/:id (finalQty) → Server re-validates stock → Recalculates Totals
        ├── Remove Item (Trash)   → DELETE /api/cart/items/:id → Removes row from MySQL → Recalculates Totals
        ├── Stock Changed Alert   → Server returns available: false / requestedQuantityAvailable: false → UI alerts customer
        ├── Inactive Product      → Marked unavailable safely without server crash
        ├── Continue Shopping     → Navigate back to /shop
        └── Proceed to Checkout   → Validates all items available → Navigate to /checkout
```

## 8. Navigation Rules

### Customer

-   The Dearr logo always returns to **Home**.
-   Main navigation should always provide access to **Shop**,
    **Search**, **Wishlist**, **Cart**, and **Account/Login** as
    appropriate.
-   From any product-related screen, the customer should have a clear
    way to continue shopping.
-   Checkout should always provide a safe way to return to the cart
    before payment.
-   A successful order should never end in a dead-end; the customer can
    view order details or continue shopping.

### Admin

-   Every admin screen should provide access back to the **Admin
    Dashboard** or the relevant section list.
-   Forms should have clear **Save** and **Cancel/Back** actions.
-   Destructive actions such as delete/deactivate should require
    confirmation.
-   Admin errors should preserve form input where possible.
-   Expired authentication should return the admin to **Admin Login**,
    then back to the requested page after successful authentication.

## 9. V1 Flow Principles

1.  **No dead ends:** Every screen has at least one useful next action.
2.  **One clear primary action:** Each important screen should have an
    obvious main CTA (Call to Action).
3.  **Short shopping path:** Browse → Product → Cart → Checkout →
    Payment → Confirmation.
4.  **Safe recovery:** Errors should explain what happened and provide a
    next step.
5.  **Admin simplicity:** Common founder tasks should take as few
    screens as practical.
6.  **Consistent navigation:** Customer and admin navigation should
    remain predictable.
7.  **Protect user input:** Failed requests should not unnecessarily
    clear forms or carts.
8.  **Server-trusted decisions:** Price, discount, stock, and payment
    outcomes must be verified by the application rather than trusted
    from browser input.

## 10. Open Flow Decisions

The following product decisions should be finalized before detailed
implementation:

1.  Guest checkout: allowed or login/signup required?
2.  Account creation: required at checkout or optional?
3.  Wishlist: available only to logged-in users or also for guests?
4.  Payment provider and exact payment flow?
5.  Shipping method and delivery status flow?

## 15. Transactional Email & Password Reset OTP Application Flows

### 15.1 Forgot Password & 6-Digit OTP Verification Flow

``` text
Customer on /forgot-password
   │
   ├── Step 1: Submit Email Address
   │      └── POST /api/auth/forgot-password { email }
   │             ├── IP rate limiting check (5 req / 15 min)
   │             ├── Account send quota check (Max 2 requests / account / UTC day)
   │             │      └── If exceeded: HTTP 429 Too Many Requests (with Retry-After)
   │             ├── Profile lookup
   │             │      ├── If account DOES NOT exist: Returns GENERIC_OTP_PUBLIC_RESPONSE (200 OK)
   │             │      │      └── No OTP record created; zero enumeration leakage
   │             │      └── If account EXISTS:
   │             │             ├── Invalidate any superseded unconsumed OTPs for user
   │             │             ├── Generate 6-digit numeric cryptographic OTP (10 min expiry)
   │             │             ├── Store HMAC-SHA256 digest in password_reset_otps
   │             │             ├── Dispatches transactional email via Resend SDK
   │             │             │      └── From: Dearr <notifications@dearr.in>
   │             │             └── Returns GENERIC_OTP_PUBLIC_RESPONSE (200 OK)
   │             └── UI advances to Step 2: OTP Verification
   │
   ├── Step 2: Enter 6-Digit OTP Code
   │      └── POST /api/auth/password-reset/verify { email, otp }
   │             ├── Constant-time timing-safe hash comparison
   │             ├── Check expiration (expires_at > NOW())
   │             ├── Check lock threshold (attempts < 5)
   │             │      ├── If invalid: increments attempts counter in DB
   │             │      │      └── If attempts reach 5: OTP locked permanently (400 Bad Request)
   │             │      └── If valid:
   │             │             ├── Atomically marks OTP consumed (consumed_at = NOW())
   │             │             └── Issues signed single-use resetToken (15-min JWT)
   │             └── UI advances to Step 3: New Password Form
   │
   └── Step 3: Set New Password
          └── POST /api/auth/password-reset/confirm { resetToken, newPassword, confirmPassword }
                 ├── Verifies signed single-use resetToken
                 ├── Validates password length and complexity (min 8 chars)
                 ├── Updates profiles.password_hash with bcrypt (cost 12)
                 ├── Increments profiles.token_version (invalidating all active JWT sessions)
                 └── UI displays Success confirmation with link to Login (/login)
```

### 15.2 Verified Razorpay Payment Confirmation & Durable Outbox Lifecycle

``` text
Customer completes Razorpay checkout modal
   │
   ├── Scenario A: Webhook Delivery (POST /api/payments/webhook)
   │   OR Scenario B: Checkout Attempt Finalization (POST /api/checkout/attempts/:id/verify)
   │      │
   │      ├── 1. Razorpay HMAC signature verification
   │      │      └── If signature mismatch: immediate HTTP 400 rejection; no side effects
   │      │
   │      ├── 2. Validate event, payment ID, currency, and amount binding
   │      │
   │      ├── 3. Atomic Database Transaction (MySQL InnoDB):
   │      │      ├── Transition orders.payment_status = 'paid', orders.status = 'confirmed'
   │      │      ├── Insert payments row (status: 'captured')
   │      │      ├── Atomically insert notification job into email_outbox:
   │      │      │      ├── event_type: 'payment_confirmation'
   │      │      │      ├── idempotency_key: 'order_payment:' + orderId (UNIQUE)
   │      │      │      ├── recipient_email & recipient_name (from trusted DB order/profile)
   │      │      │      ├── payload: { orderNumber, amount, currency, itemsSummary }
   │      │      │      └── status: 'pending', attempts: 0, max_attempts: 5
   │      │      └── Commit MySQL Transaction
   │      │
   │      ├── 4. Decoupled Asynchronous Dispatch (dispatchEmailOutboxJob):
   │      │      ├── Executes strictly AFTER transaction commit (no DB lock held)
   │      │      ├── Evaluates RESEND_EMAILS_ENABLED:
   │      │      │      ├── If false: Logs simulated send, updates outbox status = 'sent'
   │      │      │      └── If true:
   │      │      │             ├── Checks daily budget cap in rate_limits (max 80/day)
   │      │      │             │      └── If cap reached: leaves in 'pending' for next UTC day
   │      │      │             ├── Invokes resend.emails.send() with stable idempotency key
   │      │      │             ├── On 200 OK: updates email_outbox status = 'sent', provider_message_id
   │      │      │             └── On Provider Error / Timeout:
   │      │      │                    ├── Updates status = 'failed', records last_error
   │      │      │                    ├── Schedules next_retry_at using exponential backoff
   │      │      │                    └── Payment success remains 100% committed and confirmed
   │      │
   │      └── 5. Deduplication Invariant:
   │             └── Repeated webhooks hit UNIQUE index on idempotency_key:
   │                    ├── Collides safely with ER_DUP_ENTRY
   │                    └── Skips duplicate insertion and returns existing job ID
```
