# Dearr --- V1 Implementation Plan

> **V1 infrastructure:** Hostinger (Node.js hosting + MySQL + file
> storage) with Dearr application authentication.

**Version:** V1\
**Project:** Dearr E-commerce Website\
**Developer:** Beginner / Solo developer\
**Development Environment:** Antigravity IDE\
**Related Documents:** `Dearr_PRD.md`, `Dearr_TRD.md`,
`Dearr_APPFLOW.md`, `Dearr_DESIGN.md`, `Dearr_SCHEMA.md`

------------------------------------------------------------------------

## 1. Implementation Strategy

Dearr V1 should be built in dependency order:

``` text
Project Foundation
        ↓
Database
        ↓
Backend / APIs
        ↓
Customer UI
        ↓
Admin UI
        ↓
Payments & Production Integrations
        ↓
Testing / Polish / Launch
```

The first goal is not to make every screen beautiful. The first goal is
to make the system work end-to-end with real data, then refine the UI.

------------------------------------------------------------------------

# 2. Milestones

## Phase 1 --- Foundation

**Goal:** Create a clean project, connect the development tools, and
establish the Dearr design/code structure.

## Phase 2 --- Database & Core Backend

**Goal:** Create the Hostinger MySQL schema, application authentication,
file storage, and the core server-side API operations.

## Phase 3 --- Customer Storefront

**Goal:** Build the customer shopping journey from Home → Product → Cart
→ Checkout.

## Phase 4 --- Founder/Admin Dashboard

**Goal:** Give the founder enough control to manage products,
categories, discounts, and orders.

## Phase 5 --- Payments, Testing & Launch

**Goal:** Connect Razorpay, test complete flows, fix edge cases, deploy
to production, and verify the live application.

------------------------------------------------------------------------

-   [x] Storefront visibility enforced: inactive products cannot be added.
-   [x] Deactivated product resilience: existing saved items for deactivated products are marked unavailable without crashing UI or leaking hidden product details.
-   [x] Idempotent add and delete operations handling `UNIQUE(wishlist_id, product_id)`.
-   [x] Connected to customer Wishlist UI (`/wishlist`) and Product Details action buttons (`/product/[slug]`).

## 4.12 Cart API

-   [x] `GET /api/cart` (customer-authenticated via `requireUser()`; calculates trusted prices, B-14 discounts, server totals)
-   [x] `POST /api/cart/items` (customer-authenticated; adds item or increments existing row quantity idempotently)
-   [x] `PATCH /api/cart/items/:id` (customer-authenticated; sets desired final quantity with stock validation)
-   [x] `DELETE /api/cart/items/:id` (customer-authenticated; removes cart item idempotently)
-   [x] `DELETE /api/cart` (customer-authenticated; clears cart)
-   [x] Validate quantity: integer > 0; non-integers, 0, or negative quantities rejected with 400.
-   [x] Reject inactive products: adding inactive products rejected with 400.
-   [x] Deactivated product resilience: products deactivated after being added to cart return `available: false` safely without crashing GET cart.
-   [x] Check stock before allowing checkout: `(existing + requested) <= availableStock` enforced on add; `desiredQty <= availableStock` enforced on update.
-   [x] V1 Variant Pricing & Stock Rules: products with variants require an active variant selection; variant products use variant stock (no fallback to parent stock); variant price falls back to parent product price only when `variant.price` is null.
-   [x] Recalculate totals on the server: subtotal, B-14 discount engine (product > category > store, no stacking), shipping, and total calculated authoritatively.
-   [x] Decimal monetary safety: rounded to 2 decimal places to avoid floating point anomalies.
-   [x] Strict ownership & IDOR protection: client-supplied `userId`, `cartId`, `price`, `discount`, `totals` strictly ignored; queries scoped by `carts.user_id = authenticatedUser.id AND carts.status = 'active'`.
-   [x] Connected to existing Cart UI (`/cart`), CartContext, ProductActions, and Header Cart Badge.
-   [x] 62/62 automated verification tests passed in `database/verify-b16-cart.ts`.

# 15. Implementation Principle

**Build in small vertical slices, but respect technical dependencies.**

For example, do not build a beautiful Cart screen first and leave its
data disconnected.

Instead:

``` text
Cart Database
    ↓
Cart API
    ↓
Cart UI
    ↓
Checkout
    ↓
Order API
    ↓
Payment
```

That way every major part becomes functional before the next dependent
part is started.

**V1 success means: a real customer can complete a real shopping flow,
and the founder can manage the store without needing to edit code.**
